# 智能体会话消息摘要、压缩与长短期记忆管理

> 本文整合《智能体会话消息摘要和记忆管理》《智能体记忆系统完整目录结构》《智能体每日摘要流水账与总账记录功能分析》三篇原始分析，梳理 AgentScope Java（agentscope-harness）中「上下文压缩」与「长短期记忆」两条流水线的职责、协作与落地形态。

---

## 一、核心结论

一句话概括：**压缩（Compaction）与记忆（Memory）不是重复功能，而是同一条流水线上的先后接力。**

- **压缩**解决「上下文窗口装不下」——面向 token 预算，产物是窗口内的一条**摘要消息**，本身会被反复再压缩（有损链）。
- **记忆**解决「重要事实不该随压缩丢失」——面向事实保全，产物是窗口外的**磁盘文件**（流水账 + 总账），落盘即稳定、可检索、跨会话。

二者的衔接点在于：**压缩在销毁信息之前，先让记忆系统把有价值的部分「抢救」出去。**

```Plain Text
触发压缩（token / 消息数超限）
    │
    ├─ Step 2: Memory flush   ← 先把重要事实抢救到持久层（流水账）
    ├─ Step 3: Offload        ← 原始消息完整存档到 sessions JSONL
    └─ Step 4: Summarize      ← 最后才生成窗口内的摘要消息
```

如果二者功能重复，这个「先抢救、后销毁」的顺序将毫无意义。

## 二、整体架构：三层信息载体

```Plain Text
                    对话消息 (Messages)
                          │
        ┌─────────────────┼──────────────────┐
        │ 超限触发         │ 每次调用后          │ Agent 主动调用
        ▼                 ▼                   ▼
┌────────────────┐  ┌──────────────┐   ┌──────────────┐
│ Compaction 摘要 │  │ Layer 1 流水账 │   │ memory_save  │
│ 上下文窗口内     │  │ memory/       │   │  工具         │
│ （有损滚动摘要） │  │ YYYY-MM-DD.md │   │              │
│ 不可检索         │  │ append-only   │   │              │
└────────────────┘  └──────┬───────┘   └──────┬───────┘
                           │ 定期合并(≥30min)  │
                           ▼                  │
                    ┌────────────────────────▼──┐
                    │ Layer 2 总账 MEMORY.md      │
                    │ 去重/裁剪/token 上限(4000)  │

                    └────────────────────────────┘
```

| 载体 | 位置 | 写入者 | 生命周期 |
|---|---|---|---|
| Compaction 摘要 | 上下文窗口内的消息 `__compaction_summary__` | ConversationCompactor | 会话内，随历史被再压缩 |

| 总账 Layer 2 | `MEMORY.md` | MemoryConsolidator / MemorySaveTool | 跨压缩、跨会话、跨重启 |

## 三、上下文压缩流水线（Compaction）

### 3.1 触发与算法

压缩**被动触发**：当 token 或消息数超过阈值时启动。核心算法（`ConversationCompactor.java`）分四步：

```Plain Text
Step 1  Cutoff      确定截断点（保留最近窗口，压缩更早的历史）
Step 2  Memory flush   对截断前缀做记忆提取 → 写入流水账
Step 3  Offload    原始消息完整存档到 sessions/<id>.jsonl（永不压缩）
Step 4  Summarize  生成窗口内摘要消息，替换被压缩的历史
```

### 3.2 决定性证据：摘要与记忆被显式分流

`ConversationCompactor.java` 把同一个前缀切成**两路输入**：

```Java
// Keep prior summaries in the summarization input so each compaction builds on the
// previous one, but exclude them from memory flushing to avoid duplicate extraction.
List<Msg> summaryInput = new ArrayList<>(messages.subList(0, cutoff));
List<Msg> flushInput = filterSummaryMessages(summaryInput);   // ← 旧摘要被排除出 flush
```

- `summaryInput`（**含**旧摘要）→ 送入 summarization，做链式滚动摘要，保持叙事连续。
- `flushInput`（**剔除**旧摘要）→ 送入 flush，提取记忆。

注释写明理由 "avoid duplicate extraction"——**摘要 ≠ 记忆**。旧摘要要参与再次摘要（叙事连续性），但不能被当作新记忆重复提取。`filterSummaryMessages` 这个过滤器的存在，就是设计者「二者不重复」最明确的表态。

### 3.3 滚动摘要的损失模型

摘要是**有损链**：每经过一轮 rolling compression 就损失一层细节。

```Plain Text
第 1 次压缩:
  摘要 = "用户与助手讨论了数据库选型，最终决定用 PostgreSQL……"   ← 细节开始丢失
  记忆 = "- 数据库选型定为 PostgreSQL（2026-10-08 决定）
          - 连接池大小定为 20"                                 ← 原子事实，原样落盘

第 2 次压缩（摘要被再压缩）:
  摘要' = "前期完成了技术选型等准备工作……"                       ← 连接池大小也丢了
  记忆  = 不变，仍在 MEMORY.md，每次调用注入                     ← 无损
```

长会话中摘要会退化为模糊的过程梗概，而「连接池大小 20」这类具体事实只有记忆层保得住。

## 四、长短期记忆：两层架构

记忆系统实现经典的**两层架构**：流水账（Layer 1，短期、append-only）+ 总账（Layer 2，长期、LLM 合并）。

```Plain Text
对话消息 (Messages)
       │
       ▼
┌──────────────────────────┐
│  MemoryFlushMiddleware   │  ← 每次 Agent 调用后触发（节流/隔离）
└──────────┬───────────────┘
           │ LLM 提取
           ▼
┌──────────────────────────────────────────┐
│  Layer 1: 每日流水账 memory/YYYY-MM-DD.md │  append-only，带时间戳
│  所有者: MemoryFlushManager               │
└──────────────────┬───────────────────────┘
                   │ 定期合并 (≥30min)
                   ▼
┌──────────────────────────────────────────┐
│  Layer 2: 总账 MEMORY.md                  │  LLM 去重/裁剪，≤4000 tokens
│  所有者: MemoryConsolidator               │
└──────────────────────────────────────────┘
```

### 4.1 MemoryFlushManager — 流水账管理器

第一层的唯一所有者，`flushMemories()` 流程：

1. **序列化对话**：将 USER/ASSISTANT/TOOL 消息渲染为文本（跳过 SYSTEM 与内部上下文消息）。
2. **读取已有上下文**：只读 `MEMORY.md` 与当天流水账，供 LLM 参考去重。
3. **LLM 提取**：构造 SYSTEM+USER 消息对，指导 LLM 提取**新**记忆、避免重复。
4. **追加写入**：以 `## Memory Flush — {ISO时间戳}` 段落追加到 `memory/YYYY-MM-DD.md`。

关键设计：追加只写（审计安全）；不触碰 `MEMORY.md`；工具结果截断 1000 字符、工具输入截断 500 字符，防止 token 爆炸。

### 4.2 MemoryConsolidator — 总账合并器

第二层所有者，`consolidate()` 流程：

1. **读水位线**：取上次合并时间戳（`memory/.consolidation_state`）。
2. **增量读取**：只读取水位线之后修改过的流水账。
3. **LLM 合并**：将当前 `MEMORY.md` + 新流水账交给 LLM，去重、合并、裁剪。
4. **覆写总账**：用 LLM 输出整体覆盖 `MEMORY.md`。
5. **推进水位线**：记录本次合并时间点。

水位线支持分布式存储（`BaseStore`）CAS 重试（最多 5 次），store 不可用时回退本地文件。Token 上限默认 4000（约 16000 字符）。

### 4.3 MemorySaveTool — 主动保存入口

Agent 可主动调用的工具，**同时更新**两层：追加 `MEMORY.md`（即时生效）与当天流水账（`## Memory Save — {时间戳}` 标题）。它是 Agent 写入长期记忆的**唯一授权入口**，防止 LLM 用 `write_file`/`edit_file` 随意操作记忆文件。

```Java
@Tool(name = "memory_save", ...)
public String memorySave(RuntimeContext rc, @ToolParam String content)
```

### 4.4 MemoryConfig — 统一配置

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `flushTrigger` | `ALWAYS` | 刷新策略：ALWAYS / NEVER / THROTTLED |
| `consolidationMaxTokens` | 4000 | `MEMORY.md` token 上限 |
| `consolidationMinGap` | 30 分钟 | 合并操作最小间隔 |
| `dailyFileRetentionDays` | 90 天 | 流水账归档前保留天数 |
| `sessionRetentionDays` | 180 天 | 会话 JSONL 日志保留天数 |
| `model` | null（用主模型） | 可为记忆操作指定更轻量模型 |

## 五、中间件层与完整数据流

### 5.1 中间件职责

| 中间件 | 触发时机 | 职责 |
|---|---|---|
| `MemoryFlushMiddleware` | `onAgent()` 完成后异步触发 | 按隔离维度（USER/SESSION/AGENT/GLOBAL）经 `PeriodicGate` 节流后执行 flush；错误不中断主流程（`onErrorResume`） |
| `MemoryMaintenanceMiddleware` | Flush 之后，受 30 分钟最小间隔节流 | ① 归档 >90 天流水账 ② 运行 `MemoryConsolidator.consolidate()` ③ 修剪 >180 天会话日志 |

### 5.2 全景数据流

```Plain Text
Agent 调用完成
  │
  ├─① MemoryFlushMiddleware.onAgent()
  │     └─ doFlush() → shouldFlushNow()?
  │           ├─ ALWAYS   → 总是执行
  │           ├─ NEVER    → 跳过
  │           └─ THROTTLED→ PeriodicGate.tryClaim()
  │     └─ MemoryFlushManager.flushMemories()
  │           ├─ 读取 MEMORY.md（只读）
  │           ├─ 读取今日流水账（只读）
  │           ├─ LLM 提取新记忆
  │           └─ 追加 → memory/YYYY-MM-DD.md
  │
  ├─② MemoryMaintenanceMiddleware.onAgent()
  │     └─ PeriodicGate.tryClaim(minGap=30min)?
  │           ├─ expireDailyFiles()  → memory/archive/
  │           ├─ consolidateMemory() → MemoryConsolidator.consolidate()
  │           │     ├─ 读取水位线后的流水账
  │           │     ├─ LLM 合并去重
  │           │     ├─ 覆写 MEMORY.md
  │           │     └─ 推进水位线
  │           └─ pruneOldSessions() → 删除旧 JSONL
  │
  └─③ Agent 主动调用 memory_save 工具
        ├─ 追加 → MEMORY.md
        └─ 追加 → memory/YYYY-MM-DD.md
```

## 六、摘要 vs 记忆：职责对比

| 维度 | Compaction 摘要 | Memory（流水账 + 总账） |
|---|---|---|
| **解决的问题** | 上下文窗口装不下（token 预算） | 重要信息不该随压缩丢失（事实保全） |
| **载体** | 窗口内的一条消息 | 窗口外的磁盘文件（`memory/`、`MEMORY.md`） |
| **内容形态** | 叙事性过程概述 | 原子化事实 bullet |
| **触发时机** | 被动：token/消息数超限 | 主动：每次调用后 flush + 定期合并 |
| **自身命运** | 有损链：随历史被反复再压缩 | 稳定持久：append-only + 去重合并且有上限，不参与压缩链 |
| **可检索性** | 不可检索，仅上下文的一部分 | `memory_search` / `memory_get` 可按需检索 |
| **生命周期** | 会话内（依赖对话历史存活） | 跨压缩、跨会话（USER scope）、跨重启 |
| **注入方式** | 作为对话历史天然在场 | `WorkspaceContextMiddleware` 每次注入 `<memory_context>` |

**类比**：摘要 = 会议中口头的「我们刚才谈到哪了」（保持连续，越滚越模糊）；记忆 = 会议纪要里的「决议清单」（原子事实，落盘即稳定）。摘要回答「对话如何演进到这里」，记忆回答「哪些事实必须永久记住」。

### 重叠区的诚实承认

| 场景 | 重叠程度 |
|---|---|
| 短会话（从未触发压缩） | 高度重叠——记忆的唯一价值是「抗压缩」，但压缩没发生 |
| 长会话、SESSION scope | 部分重叠——都在做「会话内不遗忘」，但损失模型不同 |
| 长会话、USER scope | 几乎无重叠——摘要随会话消亡，记忆跨会话积累 |

设计者提供了裁剪开关收敛重叠：`CompactionConfig.isFlushBeforeCompact()`（默认开）可关掉压缩前 flush；`MemoryConfig.FlushMode.NEVER` 可关掉逐调用 flush、仅保留压缩时 flush。

## 七、记忆系统目录结构

### 7.1 三层物理定位

```Plain Text
${user.dir}/                                    # 项目根目录
├── (项目文件...)
└── .agentscope/
    ├── workspace/                              # ① 默认 workspace 根
    └── bus/async-tools/*.json                  # MessageBus 异步工具注册表

~/.agentscope/                                  # 用户 home（与 workspace 互不纠缠）
└── state/<agentId>/*.json                      # ② JsonFileAgentStateStore（对话状态）
```

workspace 根解析优先级：`agentscope.workspace` 系统属性 → `AGENTSCOPE_WORKSPACE` 环境变量 → `${user.dir}/.agentscope/workspace`（内置默认）。

### 7.2 workspace 内部结构（★ 为记忆核心文件）

```Plain Text
workspace/
├── AGENTS.md                       # 智能体人格与本地约定
├── MEMORY.md                       # ★ 总账 Layer 2（MemoryConsolidator 独占写入）
├── tools.json                      # MCP 配置 + 工具 allow/deny
├── memory/                         # ★ 流水账目录（MemoryFlushManager 独占写入）
│   ├── 2026-10-08.md               # ★ 每日流水账 Layer 1（append-only）
│   ├── .consolidation_state        # 合并水位线（有 BaseStore 时存分布式）
│   └── archive/                    # >90 天归档（MemoryMaintenanceMiddleware 迁移）
├── skills/<name>/SKILL.md          # 技能（workspace 级，无 namespace）
├── knowledge/  rules/  plans/      # 知识 / 规则 / 计划文件
├── subagents/<id>.md               # 子智能体声明
├── agents/<agentId>/
│   ├── sessions/
│   │   ├── sessions.json           # 会话索引（summary + updatedAt）
│   │   ├── <sessionId>.jsonl       # LLM 上下文（可被压缩）
│   │   └── <sessionId>.log.jsonl   # 完整历史（append-only，永不压缩，>180 天修剪）
│   ├── tasks/<sessionId>.json      # TaskRecord（异步任务/心跳/孤儿清理）
│   └── workspace/                  # ISOLATED 子智能体独立运行时根（递归同构）
└── .index/workspace.db             # SQLite 工作区索引（best-effort）
```

### 7.3 IsolationScope 四种隔离模式（`{ns}` 前缀）

`{ns}` 由 `WorkspaceManager.resolveRuntimeDataPath` 插入到所有经 filesystem 层的读写路径前。

| IsolationScope | namespace | MEMORY.md 路径 | 共享范围 |
|---|---|---|---|
| **USER**（默认） | `[userId]` | `workspace/<userId>/MEMORY.md` | 同用户所有会话 |
| USER（uid 缺失回退） | `[sessionId]` | `workspace/<sessionId>/MEMORY.md` | 退化为单会话 |
| **SESSION** | `[sessionId]` | `workspace/<sessionId>/MEMORY.md` | 每会话独立 |
| **AGENT** | `[]` | `workspace/MEMORY.md` | 同一 agent 所有用户共享 |
| **GLOBAL** | `[]` | `workspace/MEMORY.md` | 同一 workspace/store 全局共享 |

> `AGENTS.md`、`MEMORY.md`、`memory/`、`agents/<id>/sessions|tasks` 等运行时数据路径都带 `{ns}`；`skills/`、`knowledge/`、`rules/`、`subagents/`、`tools.json` 等智能体资产为 workspace 级共享。

### 7.4 子智能体的三种 workspace 模式

| 模式 | 行为 | 记忆落点 |
|---|---|---|
| **ISOLATED**（默认） | 完整独立运行时根，继承父 `memoryConfig` | 写入自己的 `workspace/agents/<name>/workspace/` 目录树（含独立 `MEMORY.md`、`memory/`） |
| **SHARED** | 直接复用主 workspace | 与主智能体共用同一 `MEMORY.md` 和 `memory/` |
| **自定义 workspacePath** | 指向任意目录，脱离主 workspace 树 | 指定目录下的同构结构 |

### 7.5 关键写入者权限矩阵（核心规则）

| 路径 | 唯一写入者 | 写入时机 |
|---|---|---|
| `memory/YYYY-MM-DD.md` | `MemoryFlushManager` / `MemorySaveTool` | 每次调用后（flush）或 Agent 主动保存 |
| `MEMORY.md` | `MemoryConsolidator` / `MemorySaveTool` | 定期合并（≥30 分钟）或 Agent 主动保存 |
| `memory/.consolidation_state` | `MemoryConsolidator` | 每次成功合并后 |
| `memory/archive/*` | `MemoryMaintenanceMiddleware` | 每日文件 >90 天时 |
| `agents/<id>/sessions/*` | `TranscriptMiddleware` / `SessionTranscriptWriter` | 每轮对话边界 |
| `agents/<id>/tasks/*` | `WorkspaceTaskRepository` | 异步任务生命周期 |

**核心规则**：流水账追加只写（Layer 1），总账整体覆写（Layer 2），两者由不同组件独占维护，通过 watermark 实现增量合并。

## 八、关键设计亮点

| 设计点 | 说明 |
|---|---|
| **压缩与记忆分流** | `filterSummaryMessages` 显式排除旧摘要，避免重复提取，二者职责清晰 |
| **两层分离** | 流水账追加只写（快、安全），总账定期合并（精确、紧凑） |
| **增量处理** | watermark 水位线机制只处理上次合并后修改的流水账，节省 token |
| **分布式安全** | 水位线支持 `BaseStore` CAS 重试，适配多实例部署 |
| **细粒度隔离** | 节流窗口按 USER/SESSION/AGENT/GLOBAL 隔离，防止并发竞争 |
| **LLM 去重** | 提取与合并阶段都向 LLM 提供已有内容，实现智能去重 |
| **模型可替换** | 记忆操作可配置独立轻量模型，降低成本 |
| **容错设计** | 所有异步操作均有 `onErrorResume`，记忆失败不影响主对话 |
