# 智能体会话消息摘要和记忆管理

多轮消息记忆本身就要压缩截断机制，截断的消息会形成摘要消息放入上下文，因此二者功能是不是重复了

这个问题问到了架构设计的核心。让我先验证一个关键证据——压缩与记忆提取在执行顺序上是如何协作的。\# 不重复——它们是**同一条流水线的先后接力**，代码本身就是最强证据



你观察到的重叠确实存在（都是 LLM 蒸馏、都为“长对话不丢信息”服务），但 \[ConversationCompactor\.java\]\(file:///C:/workspace/opensources/agentscope\-java\-2\.0/agentscope\-harness/src/main/java/io/agentscope/harness/agent/memory/compaction/ConversationCompactor\.java\#L44\-L55\) 的算法注释揭示了设计者的答案——压缩流程**内部包含**记忆提取，二者是包含关系，不是并列关系：



```Plain Text
触发压缩（token/消息数超限）
    │
    ├─ Step 2: Memory flush    ← 先把重要事实"抢救"到持久层（流水账）
    ├─ Step 3: Offload         ← 原始消息完整存档到 sessions JSONL
    └─ Step 4: Summarize       ← 最后才生成窗口内的摘要消息
```



**压缩在销毁信息之前，先让记忆系统把有价值的部分抢救出去。** 如果二者功能重复，这个顺序毫无意义。

## 一、决定性证据：设计者显式区分了二者



\[ConversationCompactor\.java L121\-124\]\(file:///C:/workspace/opensources/agentscope\-java\-2\.0/agentscope\-harness/src/main/java/io/agentscope/harness/agent/memory/compaction/ConversationCompactor\.java\#L121\-L124\)：



```Java
// Keep prior summaries in the summarization input so each compaction builds on the
// previous one, but exclude them from memory flushing to avoid duplicate extraction.
List<Msg> summaryInput = new ArrayList<>(messages.subList(0, cutoff));
List<Msg> flushInput = filterSummaryMessages(summaryInput);   // ← 摘要被排除出 flush 输入
```



同一个前缀被切成**两路输入**：

- `summaryInput`（**含**旧摘要）→ 送入 summarization，做链式滚动摘要

- `flushInput`（**剔除**旧摘要）→ 送入 flush，提取记忆

    

注释写明理由："avoid duplicate extraction"——**摘要 ≠ 记忆**，二者蒸馏的目标不同，所以旧摘要要参与再次摘要（叙事连续性），但**不能**被当作新记忆重复提取。

## 二、职责对比：解决的是两个不同的问题



|维度|Compaction 摘要|Memory（流水账\+总账）|
|---|---|---|
|**解决的问题**|**上下文窗口装不下**（token 预算管理）|**重要信息不该随压缩丢失**（事实保全）|
|**载体**|context window 内的一条消息（`__compaction_summary__`）|窗口外的磁盘文件（`memory/`、`MEMORY.md`）|
|**内容形态**|叙事性过程概述（“用户先要求 X，然后讨论了 Y…”）|原子化事实 bullet（“用户偏好深色模式”、“截止日期 2026\-07\-01”）|
|**触发时机**|**被动**：token/消息数超限才触发|**主动**：每次调用后 flush \+ 定期合并|
|**自身命运**|链式有损：摘要本身也会随历史增长被**再次压缩**（rolling summary），每轮都有细节损失|稳定持久：append\-only 流水账 \+ 去重合并且有 token 上限，**不参与任何压缩链**|
|**可检索性**|不可检索，只是上下文的一部分|`memory_search` / `memory_get` 可按需检索|
|**生命周期**|会话内（依赖对话历史存活）|跨压缩、跨会话（USER scope）、跨重启|
|**注入方式**|作为对话历史天然在场|`WorkspaceContextMiddleware` 每次调用注入 `<memory_context>`|

## 三、深层差异：两种截然不同的“损失模型”



这是二者最本质的区别，用一个场景说明：



```Plain Text
第 1-50 轮对话（被压缩）:
  - 决策：项目改用 PostgreSQL
  - 理由：团队熟悉度
  - 细节：连接池大小 20
  - 过程：讨论了 3 种备选方案……

第 1 次压缩（第 51 轮）:
  摘要  = "用户与助手讨论了数据库选型，最终决定用 PostgreSQL……"
        ↑ 叙事，细节开始丢失（备选方案名字没了）

  记忆  = "- 数据库选型定为 PostgreSQL（2026-10-08 决定）
           - 连接池大小定为 20"
        ↑ 原子事实，原样落盘

第 2 次压缩（第 120 轮，摘要也被再压缩）:
  摘要' = "前期完成了技术选型等准备工作……"        ← 连接池大小也丢了
  记忆  = 不变，仍在 MEMORY.md 里，每次调用注入     ← 无损
```



**摘要每经过一轮 rolling compression 就损失一层细节（有损链）**；记忆一旦落盘就稳定存在，只会在合并时被**去重合并**（语义保留）而非压缩容纳。长会话中摘要会退化为模糊的过程梗概，而“连接池大小 20”这种具体事实只有记忆层保得住。

## 四、诚实承认：重叠区确实存在



|场景|重叠程度|
|---|---|
|短会话（从未触发压缩、会话即抛）|**高度重叠**——此时记忆的唯一价值是“抗压缩”，而压缩根本没发生|
|长会话、SESSION scope|部分重叠——摘要和记忆都在做“会话内不遗忘”，但损失模型不同（叙事 vs 原子事实）|
|长会话、USER scope|**几乎无重叠**——摘要随会话消亡，记忆跨会话积累，这是摘要做不到的|



设计者甚至提供了裁剪开关来处理这种重叠：`CompactionConfig.isFlushBeforeCompact()` 可关掉压缩前 flush（默认开），`MemoryConfig.FlushMode.NEVER` 可关掉逐调用 flush，只保留压缩时 flush。**重叠区是可配置收敛的**。

## 五、结论



一个类比：



> **Compaction 摘要 = 会议进行中口头的“我们刚才谈到哪了”**（保持对话连续，越滚越模糊）
> 
> **Memory = 会议纪要里的“决议清单”**（原子事实，落盘即稳定）
> 
> 



二者回答的问题不同：摘要回答 \*“对话如何演进到这里”\*，记忆回答 \*“哪些事实必须永久记住”\*。代码里 `filterSummaryMessages` 这个过滤器的存在，就是设计者对“二者不重复”最明确的表态——**如果摘要等于记忆，就不需要防止重复提取了**。
